# 界面升级方案 · 2026-11-28

> 目标只有一个：在高复杂度任务下，让用户更快看懂「现在怎么样、下一步做什么」，同时把界面做得更干净、更有秩序。
> 保留既有像素印刷视觉语言（纸张黄 / 墨绿描边 / 硬投影），不引入构建工具与运行时依赖。

## 1. 优化目标

| 目标 | 现状 | 升级后 | 度量方式 |
| --- | --- | --- | --- |
| 3 秒内看懂任务状态 | 首屏是消息流，结论埋在最后 | 首屏第一块是任务概览：状态、质量门、用时、工序、改动、token + 最多 3 条待关注 | 首屏截图人工验收 |
| 主操作不超过 1 次点击 | 顶栏并排 4 个按钮 + 6 个 tab | 顶栏只留 1 个状态相关主按钮（开始 / 重新运行 / 停止），其余收进「⋯」 | DOM 断言 |
| 左栏先看到任务 | 9 个同权重工具链接把任务列表挤到底部 | 任务区常驻顶部，团队与工具折叠 | DOM 断言 + 截图 |
| 详情不抢注意力 | 右侧 372px 常驻、6 个 tab | 默认收起为 62px 竖条（结论 → 详情），需要时展开 | 浏览器用例断言 `insp-collapsed` |
| 长内容可控 | 评审长文、JSON 全量铺开 | 超过 400px 自动折叠，提供「展开全文」 | 截图 |
| 窄屏可用 | ≤980px 时三栏互相挤压 | 单列 + 抽屉，输入区换行 | 1366 / 820 截图 |

## 2. 诊断（当前问题）

1. **三栏同权重**：任务、消息、详情同时争夺注意力，右侧 6 个 tab 与中部阶段条重复表达「进度」。
2. **结论在底部**：进入任务默认滚到底部，先看到的是过程噪声，不是结果。
3. **左栏工具化**：「扫描 CLI / 接入工具池 / 智能分工 / 体检 / Provider / Automation / 审批」7 个入口与任务列表同级。
4. **输入区过载**：工作区、流程模式、优先级、@成员、附件、发送并排一行，认知负担高。
5. **长文无节制**：评审结论、VERDICT JSON、交付清单整块铺开，缺少层级与折叠。
6. **视觉噪音**：双层描边、密集硬投影、10–11px 小字占比过高，扫读困难。

## 3. 信息架构调整

```
左栏（任务优先）            中栏（结论优先）              右栏（按需详情）
├ 品牌 + 新建任务          ├ 任务头：标题 / 状态 / 主操作   ├ 默认收起 62px 竖条
├ 任务搜索 + 状态筛选       ├ 阶段条（5 段，可点）           ├ 展开后 6 个 tab 归并为阅读顺序：
├ 任务列表（常驻）          ├ 任务概览卡（新）               │  结论（上下文/讨论）→ 执行（链路/统计）
├ 团队（折叠）              ├ 消息流（长文折叠）             │  → 产物（工作区/文件）
└ 工具与设置（折叠）         └ 输入区（主输入 + 选项折叠）
```

- 左栏职责收敛为「选任务」，工具类入口全部下沉到「工具与设置」折叠区。
- 中栏承担「看结论 + 做决定」，不再承载配置类操作。
- 右栏从「常驻面板」变成「按需抽屉」，收起时保留明确的展开标签。

## 4. 交互流程简化

| 场景 | 旧路径 | 新路径 |
| --- | --- | --- |
| 看任务结果 | 进入 → 滚到底 → 找收口消息 | 进入 → 概览卡直接给状态、质量门、待关注 |
| 重新运行 | 顶栏「重新编排」按钮 | 顶栏唯一主按钮（已结束时显示「重新运行」） |
| 导出 / 工作区 / 设置 | 顶栏散落按钮 + 右栏 tab | 「⋯」菜单统一入口 |
| 选工作区 | 输入区常驻按钮（与优先级同行） | 保留在输入栏首项，其余选项收进「选项」 |
| 找历史任务 | 滚动长列表 | 搜索框 + 全部/进行中/待处理/已交付筛选 |
| 看执行细节 | 直接面对 6 个 tab | 概览卡「执行详情 →」一键展开右栏 |

## 5. 视觉层次改进

- **字阶**：9.5 / 11 / 12.5 / 15 / 21（像素字仅用于数字与标题），正文行高 1.5–1.6。
- **色彩语义**：主操作用橙（`--orange`），状态点用叶绿（通过）、湖蓝（运行）、黄（等待）、橙（失败），其余保持纸黄与墨绿。
- **边框规则**：卡片只保留一层 2px 描边 + 4px 硬投影；内部不再叠加第二层边框，分组改用虚线或留白。
- **间距**：8pt 栅格，卡片内边距 14–16px，模块间 12–14px。
- **可读宽度**：概览与消息列最大 960px 居中，避免超宽行。

## 6. 复杂任务呈现

1. **任务概览卡**：状态 + 质量门 + 用时 / 工序 / 改动文件 / tokens 四项指标 + 最多 3 条「需要关注」（成本待确认、质量门失败、无测试入口、同模型自审、等待原因）。
2. **长消息折叠**：内容高度超过 400px 自动折叠并加渐隐，提供「展开全文 / 收起」。
3. **默认看开头**：切换任务重置到顶部，只有停留在底部时才跟随流式输出。
4. **待确认直达**：成本超阈值的任务在概览卡直接给「确认开工」，不必再点任务卡片走弹窗。
5. **执行轨迹分层**（P1）：按阶段分组，失败优先，合并「产出 1 个文件」这类重复行。

## 7. 改造范围与优先级

### P0（本次已实施）

| 范围 | 内容 | 预期效果 |
| --- | --- | --- |

| 顶栏 | 主按钮随状态变化、新增「⋯」菜单（工作区/导出/设置/夜巡） | 主操作唯一，次要操作不占位 |

### 9.1 审计前后

| 指标 | 基线 | 收尾后 |
| --- | --- | --- |
| axe `color-contrast` serious 节点 | 5（阶段条 `small` 仅 3.16:1） | **0** |
| error | 6 | 1（静态几何误报，见 9.4） |
| warn | 36 | 15 |
| 移动端点击区 < 44×44 | 26+ | **0** |
| console / HTTP 错误 | 0 | 0 |
| CLS（desktop / light） | 0.043 | 0.000 |

### 9.2 关键改动

**交互反馈与一致性（`styles.css`）**
- 引入 `--dur-1/2/3`、`--ease-press`、`--focus`，把按钮、筛选、菜单、链接、折叠项的
  hover / active / focus-visible 收敛为同一套时长与位移，并统一 `outline` 焦点环。
- `details:not([open]) > *:not(summary) { display: none !important; }`：
  关闭状态的「选项」浮层不再生成隐藏盒子压住输入框（基线输入框重叠的根因）。
- 菜单展开、栅格切换、流式光标、滚动条统一动效；`prefers-reduced-motion: reduce` 全量降级。

**可读性与对比度**
- 阶段条 `small` 原本 `opacity: .7`，把 `#4a675d` 混成 `#80948b`（3.16:1，axe serious）；
  改为 `opacity: 1` + 实色 `#3f5d53`（夜间 `#b9d8cd`），稳定 ≥ 4.5:1。
- `skipped / blocked` 阶段由整体透明度改为实色 + 虚线边框表达弱化，不再「灰到看不清」。
- 顶栏 / 侧栏信息性微标签（连接状态、身份 chip、kicker、副标题、pill、分组标题等）
  统一到 12px 下限；英文标签同步收紧字距，避免放大后挤破阶段条。
- `public/app.js`：代码块 `<pre>` 可聚焦（`tabindex="0" role="group" aria-label="代码块"`），
  「展开全文」按钮补 `aria-expanded` 并随展开状态同步。

**响应式（≤480px）**
- 按钮 / 输入框 / 筛选 / 阶段节点补 `min-height: 44px`，图标按钮补 `min-width: 44px`
  （WCAG 2.5.8，与审计同口径）。
- 顶栏改「标题行 + 操作行」两行：触摸区放大后不再把任务标题挤成「给…」；
  装饰性 kicker 在窄屏让位给标题。
- 概览卡指标保持两列，输入区行高放宽。

## 10. 委托台：从「监控台」到「委托台」（第二轮）

> 前两轮把控制台做对、做干净，但范式没变：仍是用户盯着 AI 干活、自己从过程里翻结论。
> 本轮换掉前提：系统主动收敛过程，只在需要人拍板时打扰。

### 10.1 设计目标

| 从 | 到 |
| --- | --- |
| 首屏 = 消息流 / 概览指标 | 首屏 = 需要你拍板的事 |
| 用户自己找结论 | 系统把结论与待办推送到面前 |
| 过程越复杂，信息越多 | 复杂度留在后台，按需展开 |
| 交互 = 滚动 + 逐层点开 | 交互 = 一次决策 + 随时追溯 |

卖点从「看得清」变成「不用看」。

### 10.2 决策信号（不新增后端字段）

`public/lib/decisions.js` 把状态里已有的信号聚合为最多 3 张卡，纯函数、可单测：

| 信号 | 来源 | 动作 |
| --- | --- | --- |
| 成本待确认 | `pendingConfirmation` + `costEstimate` | 确认开工 → `POST /api/tasks/:id/confirm`；查看估算 → 展开详情 |
| 命令待审批 | `S.approvals` 中 `pending` | 批准/拒绝 → `PATCH /api/approvals/:id` |
| 质量门失败 | `quality.status === "failed"` | 查看失败详情 → 展开详情 |
| 无测试入口 | `quality.status === "no-test-entry"` | 查看工序 |
| 方案降级裁决 / 多样性不足 | `debate.decision` + `diversity` | 查看方案对比 → 切到讨论 tab |
| 同模型自审 | `quality.selfReview` | 查看评审 |
| 等待原因 | `waitingReason` | 查看链路 |

所有动作复用已有 API 或纯导航，不引入新后端能力，也不承诺不存在的操作。

### 10.3 界面结构

- **决策态**：标题「需要你拍板 N 件」+ 最多 3 张卡（黄 / 青 / 红语义色、橙色主按钮），容器硬投影切为橙色形成视觉焦点。
- **静默态**：无决策项时只显示「无需你介入」与一句结论，不铺陈过程。
- **后台进度**：5 段阶段条（已完成 / 进行中 / 异常 / 待执行）+ 用时、工序、改动文件、Tokens 四项指标 + 「执行详情 →」。
- **状态驱动情绪**：决策标记与进行中阶段条做 1.8s 呼吸动效，`prefers-reduced-motion` 全量降级。
- `#missionCard` 的 id 保持不变（浏览器用例断言不破），class 由 `.mission` 改为 `.decision-desk`。

### 10.4 响应式

≤720px 指标改两列、标题缩到 16px；≤480px 决策卡单列、按钮 ≥44×44，顶栏保持「标题行 + 操作行」两行。

## 11. 意图画布（Intent Canvas）· 2026-11-28

### 11.1 优化目标与范式

前两轮解决「把控制台做对、把决策提到首屏」，第三轮换掉**输入范式**：原先一段自由文本
`textarea` 把目标、约束、分工全压在一起，用户写完就失去结构，后端也只能靠猜。意图画布把「描述需求」
变成「摆放意图」——**目标 / 子目标 / 约束**是可见可拖的卡片，右侧实时映射成 5 个成员工位，
开工时再收敛成一段结构化文本。核心卖点是「先把意图摆清楚，再让团队开工」。

**零后端改动**是硬约束，也是可行性依据：`POST /api/tasks` 只显式读取
`goal / flowMode / priority / workspace / isolation / mode / speed / autoRun / clientMessageId / tenantId`，
未知字段静默丢弃，`goal` 是唯一且无长度上限的自由文本。画布因此把卡片序列化成多行 `goal` 复用
`createTask()`，不改路由、不改 store、不改任务模型。序列化**首行恒为自然语言主目标**，因为
`store.mjs` 用 `goal.slice(0, 26)` 生成 `title`，若首行是「目标拆解：」会污染任务标题。

### 11.2 信息架构

画布挂在空态 `#hero` 的 `.hero-compose` 内，与 `#heroInput` 共存、互斥显隐，共用同一个开工按钮语义：

```
.compose-head    [INTENT CANVAS / 意图画布]        [文本 | 意图画布]
.ic-foot         [N 卡片 · N 硬约束 · N 软约束 · N 工位] [先讨论后实施] [清空画布] [开工 →]
.ic-grid
  ├ 01 主目标     输入框 + 子目标卡片（可拖）+ 添加行
  ├ 02 约束       10 条预置约束库（点击加入/移除）+ 自定义约束 + 已加入卡片（可拖）
  └ 03 成员落位   5 个工位（Nova/Forge/Kilo/Probe/Lens），自动 / 已指定 两种标记
    04 意图摘要   折叠预览「将发送给团队的内容」
```

进入画布模式时 `.page.ic-mode` 收起营销式首屏装饰（h1 / lead / eyebrow / hero-side / stats / team），
把 hero 宽度从 780px 放宽到 1120px，让中栏真正成为编排工作台；切回文本模式全部恢复。
工具条「指标 + 清空 + 开工」放在画布**顶部**而非底部，保证首屏可见（底部被固定 composer 挤压）。

### 11.3 实时分工推导（核心算法）

`deriveAssignments(state, agents)` 在 `public/lib/intent-canvas.js`，纯函数、浏览器与 Node 共用：

1. 从 `S.agents` 取 `seat !== false` 的主执行席位，按 `ROLE_ORDER` 建 5 个工位（含空工位）。
2. 每张卡带 `roleHints`：预置约束在库里显式声明（如「先写测试」→ tester，「不改现有 API」→ architect，
   「安全与鉴权」→ architect+reviewer）；子目标/自定义约束走关键词启发式（测试/文档/接口/安全/性能/评审/UI）。
3. **显式指派优先**：用户拖过或点选过的卡片记在 `state.assignments[cardId]`；否则取 `roleHints` 中
   第一个实际存在的席位；都不命中落到 planner。
4. 工位同时展示 `自动`（虚线）与 `已指定`（实线橙边）两种小卡，用户一眼能看出哪些是自己定的、
   哪些是系统推断的，可随时用卡片上的 `↩` 回落自动。

交互提供两条等价路径：HTML5 `dragstart/dragover/drop` 拖拽，以及**点选卡片 → 点工位**的两步式
（键盘 Enter / Space 同样可用），`aria-live` 播报每次指派结果。

### 11.4 序列化格式

```
做一个支持并发安全的待办清单 API，带单元测试和技术方案文档      ← 主目标（title 取前 26 字）

目标拆解：
- 设计并发控制与数据模型
- 提供 REST 接口与 JWT 鉴权

硬约束（必须满足）：
- 先写测试
- 不改现有 API

软约束（尽量满足）：
- 中文技术文档

建议分工（供规划师参考，实际以动态编排为准）：
- Forge（架构）：设计并发控制与数据模型、[约束] 不改现有 API
- Probe（测试）：提供 REST 接口与 JWT 鉴权、[约束] 先写测试
```

分工段措辞明确写「供规划师参考」，避免后端 planner 误当成强制编排。`no-op` 时只返回主目标，
不产生空段。开工后**保留约束与分工、只清空主目标**：一套工程规范可以复用为模板，同时
`canvasReadiness()` 会因主目标为空禁用开工，防止误重复提交。

## 12. 成员泳道与时间回放 · 2026-11-28

### 12.1 目标与数据模型

> 把混在一条时间线里的过程消息，变成「按人分行的泳道拓扑 + 可拖动的时间轴回放」，让用户直接看出谁在并行、谁在等待、哪里被质量门挡住。

纯前端模块，零后端改动：

- `public/lib/swimlane.js` 只从 `task.messages` 派生：
  - `deriveLanes()` 按成员名分泳道，系统 / 质量门 / 计划 / 摘要 / 决策消息归入系统泳道，用户消息单独一条；
  - 连续同类消息按 ≤45s 时间窗折叠成块（实现 ×12，而不是 12 个点）；
  - `buildTimeline()` 汇出总时长、并行度峰值、里程碑、瓶颈窗口与最长空窗；
  - `replaySnapshot()` 给定任意毫秒时刻，返回每条泳道的 active / completed / upcoming 状态。
- 消息缺时间戳时按输入序号补虚拟时间，保证稳定渲染；乱序时间戳统一排序后派生。

### 12.2 界面与交互

- 工作台「执行详情」新增「泳道」视图；每行一个成员，横向按时间比例排列，颜色沿用成员现有配色。
- 质量门、方案裁决、完成等里程碑横跨泳道，一眼看出失败前的最后活跃者。
- 底部 scrubber 支持拖动与播放；拖动后立即显示「此刻谁在做什么」快照。`prefers-reduced-motion` 下播放改为步进。
- 泳道块可聚焦并有可读 label；scrubber 用 `role="slider"` + 键盘步进；快照容器 `aria-live="polite"`。
- ≤980px 泳道纵向堆叠但保留时间比例；≤480px 触摸区 ≥44px、12px 字阶下限，时间块按比例排列。
